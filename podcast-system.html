The short version

  • I give it an article link, an X post, or just a topic.
  • It gathers real sources, writes a two-host dialogue, then fact-checks the script before any audio exists.
  • A GPU at home reads the script out loud. Voices and audio cost nothing to run.
  • I listen in a phone app. I hold a button, ask a question out loud, and hear an answer that knows where I am in the episode.
  • Total moving parts: one app process, one database file, one scraper, one speech service, one language model.

What it does

Three kinds of input, one kind of output: an episode with a transcript and a source list.

I read less than I want to. Links pile up. So I built something that turns the pile into audio I can play on a walk.

It takes three inputs:

  • An article URL. A scraper pulls the main content as clean text.
  • An X post. A resolver API returns the post, the rest of the author's thread, and any quoted post. If the post links to an article, the scraper fetches that too.
  • A topic. No link needed. The language model searches the web and writes a brief with citations.

I paste into the app, or share a link from my phone's share sheet. Either way the episode joins a queue and I stop thinking about it.

The pipeline

Five automatic stages, then it lands in my library. One stage runs at a time, and each one writes its result to the database before the next one starts.

The order matters in one specific way: the fact-check runs before the GPU does. Audio is the slow, hard-to-edit part. I want the text correct while it is still cheap to change.

The parts

Five components. One of them is a file.

PartJobWhere it runs
App service Serves the API, serves the phone app, and runs the pipeline worker in the same process Home server
Database One SQLite file. Holds episodes, chat turns, and queue state Disk, next to the audio files
Scraper Turns a URL into clean text and metadata, with its own headless browser Self-hosted, private network only
Speech service Owns every audio model: episode voices, answer voice, speech-to-text, timestamp alignment Home server, on the GPU
Language model Topic research, dialogue script, fact-check pass, and spoken answers Hosted API — the only part I pay per use

There is no message broker and no second database. At one-person volume, a loop over a table is the whole queue. Audio files sit on disk and the database stores their paths.

The speech service loads three models. The two small ones stay in memory. The large episode voice model loads for a render and releases its memory afterwards, which keeps the whole thing inside the GPU's budget.

The stack, named

Nothing here is exotic. One runtime, one file database, four models, and a scraper I host myself.

LayerWhat I useNotes
Runtime and API Bun with TypeScript, Hono for routing One process serves the API, hosts the app, and runs the pipeline worker
Database SQLite through Bun's built-in driver Write-ahead logging on. Two tables: episodes and chats
Phone app React, built with Vite, installed as a PWA Media Session API for lock-screen controls. HTTP range requests for scrubbing
Article scraping Firecrawl, self-hosted Open source, no cloud key. Brings its own headless browser, queue, and cache containers
X posts The FixTweet resolver API X blocks scrapers, so I ask a resolver for the thread instead of loading the page
Language model Ollama Cloud, running GLM 5.2 Also handles topic research through its web search and fetch tools. Swapping the model is one setting
Episode voices VibeVoice 1.5B Built for multi-speaker dialogue. Renders the full episode in one pass, about 7 GB of VRAM
Answer voice Kokoro 82M Small and near-instant, which is what a spoken answer needs
Transcription faster-whisper (distil-small.en) Does two jobs: my recorded questions, and word timings for the transcript
Speech service Python with FastAPI Four endpoints. It owns the GPU and every audio model
Packaging Containers, one compose file Only the app publishes a port. Everything else talks over the private container network

Two choices in that table carry the most weight. Bun means the API, the worker, and the tests share one runtime with no build step for the server. SQLite means the queue, the episode records, and my question history are one file I can copy.

The paid voice provider I keep on the bench is ElevenLabs. It sits behind the same interface as the local speech service, so turning it on is a config change and not a rewrite. I have not needed it.

Maya and Sam

The two hosts are markdown files. I edit their personalities in a text editor, and the next episode sounds different.

Every episode has the same two voices. Maya hosts — she is my stand-in, and she asks the question I would actually ask. Sam explains — calm, precise, heavy on analogies.

Neither of them lives in the code. Each one is a markdown file on disk with three parts:

  • Voice and style. Maya talks like a smart friend, not an interviewer with cue cards. Sam defines a term in one breath and moves on.
  • Role in the episode. Maya opens on why the topic matters, draws Sam out, pushes for concrete examples, and recaps the takeaways at the end. Sam carries the substance in digestible chunks.
  • A list of don'ts. Maya must not explain the material — that is Sam's job. Sam must not add a fact, a number, a name, or a date that is not in the dossier.

Those don'ts do real work. Part of the factual discipline lives in the persona file rather than in the pipeline, because it is a rule about how a character speaks.

The files are read fresh for every episode, so an edit applies to the next one with no rebuild and no restart. If a file goes missing, a short built-in description takes over so script generation never breaks over a typo in my prose.

How they get their voices

Each host has one short reference clip: a female voice for Maya, a male voice for Sam. The voice model reads the identity out of that clip, so I never trained anything.

Before rendering, the script is flattened into labelled lines — Maya becomes Speaker 1, Sam becomes Speaker 2 — and the model receives one reference clip per speaker. Because the whole episode renders in a single pass, the two voices stay themselves from the first line to the last. Rendering line by line would drift.

One rule when I retune them. The persona file and the reference clip have to agree about gender. Editing Maya's file into a male character while the clip stays female produces an episode that fights itself.

What the show sounds like

The script prompt fixes the opening. Maya welcomes you to the show, both hosts say their names, and Maya names the topic and why it matters right now. Two or three short turns, no takeaways given away.

Then it runs on the material rather than a clock. A rich source produces a long episode — often 30 minutes or more — because the prompt sets no target length and forbids padding. Maya closes by recapping the three to five points that mattered, and signs off.

Keeping it true

Three layers, because a prompt that says "do not invent facts" is not a control.

  1. Grounding. The script writer only sees the dossier. It never sees the raw internet, and it never sees my question history.
  2. Verification. The fact-check pass extracts each claim and checks it against that same dossier. For topic episodes it also searches the web again. Unsupported claims get cut or hedged in one bounded revision.
  3. Traceability. Every episode page lists its sources and its claim verdicts. Mid-episode answers come from the same dossier, so I can always ask where a fact came from.

This is the fact-check tab on a finished episode. Each row is one claim the hosts made, the verdict it received, and the sentence from the dossier that supports it.

I read it more often than I expected. When a claim sounds surprising, the answer is two taps away, and the wording underneath is the source's, not the model's.

Longer episodes produce more rows than I will ever read end to end. That is fine — the list is there for the one claim I want to check.

Honest limit. This makes invented facts rare and catchable, not impossible. The dossier itself can carry a source's mistake. The source list is the audit trail, not a guarantee.

One more rule holds everywhere: the full source text never leaves the server. The app receives the source links and the transcript. It never receives the raw dossier text.

Asking questions mid-episode

Hold a button or say the wake word. Playback pauses, the answer comes back spoken, and playback resumes where it stopped.

  1. I hold the mic button, or I say the word "question" while the wake word is armed.
  2. Playback pauses. The app notes my exact position and records me.
  3. A local speech-to-text model turns my recording into text. My voice never leaves the house.
  4. The language model answers. It receives the source list, the dossier, the full transcript with timestamps, my last few questions, and how far into the episode I am.
  5. A small local voice model speaks the answer. When it finishes, the episode resumes at the same second.

That position matters more than I expected. The answer is told not to spoil later parts of the episode unless I ask. So "wait, what did he just mean?" gets answered from what I have actually heard.

Every question and answer is stored against the episode, so the transcript of my own confusion is part of the record.

The queue, and what happens when a stage fails

One loop, one episode at a time, five attempts, then the episode is marked failed and left alone.

The worker ticks every two seconds. Each tick claims the oldest episode that is due and runs exactly one stage. If work remains, the next tick fires immediately.

Concurrency is one, on purpose. A single loop cannot double-render an episode, so I need no locks and no lease timeouts.

Failures are ordinary and expected:

  • A stage that throws leaves the episode's status untouched. It stays claimable.
  • The retry delay doubles each attempt, starting at 30 seconds.
  • After five attempts the episode is marked failed with the stage name and the error, and the app shows it as failed.
  • Every status write states the status it expects to find first. A write from the wrong starting point changes zero rows and raises an error instead of quietly moving an episode backwards.
  • If the process dies during a render, the next boot finds the episode stuck at synthesizing and sends it back to verified to render again. GPU time at home is free.

The app

Sourced.fm, served by the same process as the API, built for walking around with headphones.

What it does while an episode plays:

  • The transcript follows the audio. Each line has a real timestamp, so the current line highlights itself. Tapping any line jumps there.
  • Lock screen controls work, including skip back 15 seconds and skip forward 30.
  • Scrubbing works properly because the audio route serves byte ranges, not just whole files.
  • Sources and fact-check notes sit behind two tabs next to the transcript.

Outside the player there are two ways to organise the pile:

  • Playlists. Ordered queues I can reorder. When one episode ends the next one starts by itself. Playlists stay on the device.
  • Listened marks. An episode marks itself listened when it plays to the end, and I can toggle the mark by hand. The library filters to All, Unlistened, or Listened, and the home screen shows what I still have to hear.

Listened state lives on the server, not in the browser. I finish an episode on my phone and my laptop already knows. Playlists made the opposite choice, and that split is deliberate: order is personal to a device, progress is not.

Limits I accepted

Four things I will not fix, because they are properties of the platform, not bugs.

  • The mic needs a secure connection. Browsers refuse microphone access otherwise, so the app must be reached over HTTPS. This is why the voice features are dark on a plain local address.
  • The wake word needs the app in front and the screen on. Phones suspend a web app's microphone when the screen locks. Locked screen means playback controls only.
  • Use headphones for the wake word. On a speaker the mic hears the hosts, and a host who says "question" can trigger it.
  • Rendering takes minutes, not seconds. The episode voice model is doing real work on a consumer card. For a batch pipeline I never watch, minutes are fine.

Also worth saying plainly: a scraper without commercial anti-bot help will lose to some sites. Those episodes fail at the source stage and I see the reason in the app.

What it costs

Audio is free. Text is not.

Every voice in the system runs on hardware I already own, so speech costs electricity. The only metered spend is language model tokens: research, script, fact-check, and each spoken answer. A hosted voice provider stays behind a swappable seam in case I ever want one, and turning it on would cost more per episode than everything else combined.

If you want to build this

The shape is more useful than the tool choices.

  1. Make the dossier a real object. Every later stage reads from it and nothing else. This one decision is what makes the fact-check possible.
  2. Put the verification before the expensive stage. Text is cheap to fix. Audio is not.
  3. Let the status column be the queue. One loop, one row at a time, a guard on every status write. A broker is a later problem, if ever.
  4. Store timestamps per transcript line. A follow-along transcript, tap-to-seek, and position-aware answers all fall out of that one field.
  5. Decide per feature whether state belongs to the device or the account. I got playlists and listened marks right only because I asked the question separately for each.

The stack underneath is replaceable. Swap the scraper, swap the voices, swap the model. The five stages and the dossier rule are the parts I would keep.

Written from my own build notes. Nothing here needs my hardware in particular — a machine with a mid-range GPU, a scraper, and a hosted language model is the whole ingredient list.
